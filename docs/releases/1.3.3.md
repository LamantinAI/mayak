# Mayak 1.3.3

Патч добавляет явное разделение режимов запуска контейнера через `APP_STARTUP_MODE` и устраняет ложное утверждение в диагностике `/health/ready` при неизвестной образу ревизии БД.

## Что изменилось

- **Режимы запуска `entrypoint.sh` (`APP_STARTUP_MODE`, только через env).**
  - `migrate-and-serve` (значение по умолчанию, когда переменная не задана) — штатный preflight (`Settings.validate_runtime()`), применение миграций Alembic при `POSTGRES_ENABLED=true` и старт HTTP-сервера.
  - `migrate` — штатный preflight и миграция схемы (либо штатный no-op при `POSTGRES_ENABLED=false`), после чего контейнер завершается с кодом `0` без запуска приложения.
  - `serve` — штатный preflight и запуск HTTP-сервера без выполнения миграций на старте; позволяет запускать рабочие реплики под ролью PostgreSQL без прав DDL.
  - Позиционные аргументы командной строки, пустое или неизвестное значение `APP_STARTUP_MODE` и невалидная runtime-конфигурация отклоняются **до обращения к базе данных**. Автоугадывания режима нет.
  - Переменная проброшена в `docker-compose.yml` (`${APP_STARTUP_MODE-migrate-and-serve}`) и задокументирована в `.env.sample` и `README.md`.

- **Честный диагностический текст `/health/ready` и граница контракта готовности.**
  - Контракт rolling deploy сохранён: когда `alembic_version` содержит ревизию вне дерева `alembic/` текущего образа (`not revisions <= known`), `/health/ready` по-прежнему отвечает `200` (`healthy`), чтобы реплики `N-1` не выводились из балансировки сразу после expand-миграции `N`, а откат `N-1` в режиме `APP_STARTUP_MODE=serve` оставался работоспособным.
  - Исправлен текст `checks.database.message`: вместо утверждения `its schema is newer than this code` возвращается `Database connection successful; recorded schema revision is unknown to this code (allowed for rolling deploys; schema compatibility is not verified)`.
  - `/health/ready` **не доказывает совместимость приложения с конкретной БД**: ошибочно подключённая чужая или несовместимая база с неизвестным идентификатором ревизии также получает `200` на `/health/ready` и падает с `500` на первом предметном запросе. Перед переключением трафика необходим **gate независимой предметной пробы** по рабочему маршруту сервиса, либо **строгий продуктовый контроль схемы**, если платформа управляет раскаткой исключительно по `/health/ready`.

## Двухшаговое внедрение в существующих продуктах

Образы, собранные на базе **Mayak `v1.3.2` и старше, игнорируют `APP_STARTUP_MODE`** и при `POSTGRES_ENABLED=true` безусловно выполняют `alembic upgrade head` на старте. Если выпустить релиз `N` с новой миграцией и этим `entrypoint.sh`, когда предыдущий образ `N-1` ещё использует `entrypoint.sh` из `v1.3.2`, откат на `N-1` (даже с `APP_STARTUP_MODE=serve`) вызовет `alembic upgrade head` поверх ревизии `N`, упадёт с `Can't locate revision identified by '<rev_N>'` и завершится с кодом `1` до запуска сервера.

Безопасный порядок перехода — строго в два шага:

1. **Шаг 1 — опорный релиз (`N-1`):** перенести новый `entrypoint.sh` (и `health.py`) и выкатить продукт **без новых миграций БД**, чтобы актуальная точка отката уже поддерживала `APP_STARTUP_MODE=serve`.
2. **Шаг 2 — expand-релиз (`N`) и раздельный запуск:** выпускать аддитивные (expand-совместимые) миграции, выполнять `APP_STARTUP_MODE=migrate` отдельным шагом под ролью с правами DDL, а рабочие реплики `N` (и при необходимости отката — `N-1`) запускать с `APP_STARTUP_MODE=serve` (в том числе под ролью БД без DDL) и независимой предметной пробой перед подачей трафика. Удаление старых колонок/таблиц (contract) выносить в следующий релиз после вывода `N-1`.
